E2EE Capture Viewer

Opens a capture exported by the E2EE Inspector. Everything happens in this tab: the file is not uploaded anywhere, and decryption uses only the keys inside the file, the same keys your browser received in the meeting.

1. What you received

Each row is one stream of media your browser received from the meeting server. "Encrypted" means the frame carries the E2EE trailer (IV and key index) and its content is AES-GCM ciphertext. Press play to see and hear what the server delivered, then what it becomes with the keys.

2. The keys your browser received

Each participant's browser makes its own random media key and sends it to every other participant inside an Olm-encrypted message. These are the keys your browser was handed. The fingerprint is a short hash: compare it with the sender's capture without revealing the key.

3. How the keys travelled

Everything the meeting server relayed for the key exchange. The first messages set up an Olm session from public identity keys (check them with the emoji verification). The media keys travel inside key-info messages as Olm ciphertext, which the server cannot open.

4. Did a media key leave your browser?

While the Inspector ran, everything the meeting page sent out was searched for the media keys, as raw bytes, hex, base64 and number lists. This catches the app (or a tampered build) sending a key out in a readable form. It cannot see a key that was first encrypted or disguised: that is what code verification is for.

5. Compare with the other participant's capture

Load the capture the other person exported from the same meeting. If the server had secretly put itself between you during the key exchange, your two browsers would hold different identity keys for each other. This is the same protection as the emoji check, done by comparing the files.
